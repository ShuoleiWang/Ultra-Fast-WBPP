# Changelog

All notable changes are documented here. The format follows Keep a Changelog and the project uses Semantic Versioning after the first stable release.

## [Unreleased]

### One engine boundary, one name, readable orchestration

- The desktop runs the engine's command line for every operation and reads its capabilities from `doctor --json` (new `status.metalReady`). The NDJSON worker protocol that no product path used is removed with its `worker`/`controller-plan` commands, the desktop's `start_pipeline`/`cancel_pipeline` commands, the Rust `app-core` crate and the `protocol/` schemas; the astrometric receipt the desktop re-validates now lives in the desktop crate. The engine sidecar manifest is v3 (`engine.version` instead of the handshake capabilities) and packaging verifies the frozen engine through the same `doctor` self-report.
- Removed paths that never ran in the product: the Siril adapter (probed by every run, executed by none), the QC tool's PixInsight input-tree preparation (`prepare-wbpp`, `apply-wbpp-plan`), the `e2e`/`project_e2e` module aliases, the `openastroflow-engine`/`openastroflow-worker` console scripts, the `benchmarks/evaluate_masters.py` and `master_tolerance_gate.py` forwarders (use `tools/validation/`), and the hardware-profile wire mapping only the worker used.
- One name. Code identifiers use `ufwbpp`: Python packages `ufwbpp` (in `packages/engine`) and `ufwbpp_registration` (in `packages/registration`), `ufwbpp_native_*` C symbols, the `ufwbpp-engine` sidecar and `UFWBPP_*` environment variables (the `OPENASTROFLOW_*` names are no longer read). Names a user sees spell out the product: the `ultra-fast-wbpp-desktop` binary, the bundle identifier `io.github.shuoleiwang.ultra-fast-wbpp` (macOS treats the app as new: file-access prompts appear again and the remembered output folder resets) and the data root `~/.ultra-fast-wbpp` / `%LOCALAPPDATA%\Ultra-Fast-WBPP`. An existing `~/.openastroflow` / `%LOCALAPPDATA%\OpenAstroFlow` root is used in place, so installed catalogs stay verified. The `OAF*` FITS keywords and the content-addressed catalog manifests are unchanged; product version strings in receipts and the colour/mosaic `OAFVERS` card now read `ultra-fast-wbpp-…`. The patched Windows SEP build is `1.4.1+ufwbpp.1`.
- Readable orchestration. `pixel_pipeline._run_portable_pipeline_fits` (1,822 lines) is a sequence of stages around a `_RunPlan` (`_plan_run`, `_build_calibration_masters`, `_plan_light_jobs`, `_calibrate_and_register_lights`, `_integrate_group`); `run_e2e` (1,226 → 613 lines) delegates source validation, screening, counterfactual exclusion and solving to named functions. Canonical JSON and SHA-256 forms live once in `integrity.py` (the six copies disagreed only in the drizzle receipt, which now writes UTF-8 like the others). The native integration kernels are `FusedIntegration` instead of `FusedLnIntegration`; the retired LocalNormalization no longer appears in receipts, the tuning table, the path budget or the desktop request.
- The desktop's start conditions are one pure function (`startBlockers`) behind both the start button and the launch bar's list. The frontend source is formatted with Prettier and `format:check` runs in CI and `make frontend-test`.
- Pixels are unchanged: the NGC 7331 reference project (61 Lights, L/R/G/B, M3 Pro, macOS 27) produced byte-identical L/R/G/B masters against a baseline built from `02109dd` (L `40ee1b8a5c03a31a`, R `a9479170348d9289`, G `a20bb3c110ad2738`, B `263149bc994caec9`); the LRGB pixel data is identical and only its `OAFVERS` card and checksum cards differ (the checksum comments carry a write timestamp, so that file is not byte-reproducible between any two runs). Wall time 90.8 s against 94.9 s, QC cache off. About 19,500 lines of code and tests were removed net, not counting the Prettier reformat of the frontend.

Flags remain advisory and no longer pre-drop frames in the GUI; remove Apply Flags and legacy REVIEW approval controls. The headless default is unchanged. The native controller rejects incomplete or stale review and binds the manual selection to the session manifest and imported Lights.
- Fix blank native WebKit Blink previews by drawing decoded images to canvas instead of using transformed IMG layers. Show loading/error placeholders, provide retry, and count only main-view paints as seen; playback waits for paint, starts paused and stops at the channel end. Unavailable frames require an explicit drop.
- Retain the independently chosen reference and common photometric normalization/stretch per channel; forward imported Master Darks and Master Bias alongside Master Flats for preview calibration.

### Added
- Blink-style screening ([recipe](docs/recipes/blink-screening.md)). The desktop's primary screening path is now **Blink & select**: the worker's new `blink-measure` command measures every Light once (the quality check's measurement, analysis and unchanged gate), computes per-channel *flags* with absolute cross-night criteria that the gate's nightly-relative model does not have (`lightframeqc.blink_flags`, policy `blink-flags-v1` with a canonical digest: sky relative to the channel's clean sky, star count relative to the channel's best, extinction, background shape against the reference, flat-corrected gradient amplitude when master flats are supplied, FWHM, elongation, unregistrable and star-less frames, plus the gate's own evidence mapped to flags), chooses a *reference frame* per channel by a PSF-signal-weight proxy (`lightframeqc.blink_reference`, `psf-signal-weight-proxy-v1`: transparency² over preview noise², divided by the PSF area, times roundness and detection completeness, with a dither-centrality tie-break), and renders every frame registered and photometrically normalised to that reference with one shared asinh stretch per channel at 1/8 scale (filmstrip, JPEG) and 1/4 scale (zoom, PNG) into a create-only session under the platform cache root (`blink_previews.py`, `blink_session.py`; manifest `blink-manifest-v1`). A flag sets a default decision (EXCLUDE → drop, ATTENTION → keep) and a reason; nothing is excluded silently, and evidence-insufficiency gate codes become notes. The new `BlinkView` (channel chips, shared-viewport stage with compare mode, flagged-first filmstrip grouped by night with *Drop night*, playback at 2–8 fps, keyboard for every decision, apply-flags, undo, kept/total per channel in the launch bar, English and Chinese) sends the decisions with the run as a `selection-v1` file (`ultra-fast-wbpp run|run-project --selection`, or the request's top-level `selection`; recipe policy `explicit-v1`; mutually exclusive with review approvals, `SELECTION_POLICY_CONFLICT`). The run recomputes the gate, flags and reference from the same functions, replaces the gate's admitted set with the selection (a KEEP on an unregistrable frame fails closed, `SELECTION_UNREGISTRABLE`; a KEEP over a HARD_FAIL is honoured and counted), writes `qc/blink.json`, records `qualityControl.selection` (digest, origin, counts, one record per frame) and `qualityControl.blink` (the blink reference next to the pipeline's registration and normalization references) in the receipt, and lists every drop and override in the screening summary (`USER_DROP`, `USER_KEEP_OVERRIDE`). The blink reference is not the pipeline's reference, and registration, normalization and integration are untouched: an identical admitted set produces bit-identical products whichever route admitted it. A run started without a blink session keeps the legacy gate and says so; the legacy review page stays optional. The flags and the reference rule are held by a share-safe regression fixture of the six-night NGC 6822 campaign (`test_blink_ngc6822_regression.py`: all 23 moonlit L frames pre-dropped, no dark-night frame excluded, every EXCLUDE agreeing with the maintainer's hand selection but one light-cloud frame).
- Documentation: [docs/features.md](docs/features.md) states the advantages over PixInsight WBPP and the noteworthy features with the evidence behind each claim (and what the project does not do), [docs/README.md](docs/README.md) maps every page, [AGENTS.md](AGENTS.md) and [CLAUDE.md](CLAUDE.md) guide contributors and coding agents (rules, commands, verification, gotchas), and both READMEs are rewritten around them with the current numbers. Stale statements corrected across the tree: ASTAP is a verified final-gate backend with the managed indexes, Bayer Lights are supported, the worker imports no GPL library, registration is projective, the native kernels are installed from the Release build and link the static C runtime on Windows.
- Windows x64 support ([docs/windows.md](docs/windows.md)). ASTAP is a strict final-gate solver: after `astap_cli` solves (with `-sip` distortion terms when the CLI offers them) the engine detects stars on the master, projects the Tycho-2 stars of the densest managed Astrometry.net index that covers the field through the WCS, matches them one to one and records residuals, matched count, parity, the correspondence table and the byte-bound index identities in the same shape as the astrometry.net adapter (`openastroflow_engine.catalog_correspondence`, adapter `astap-process-v4`; the adapter passes ASTAP the field height its `-fov` expects, derived from the engine's width hint and the image aspect); without the managed index set ASTAP stays diagnostic-only. The doctor reports `scienceReady` per solver backend, the desktop recipe uses `backend: auto`, the solver panel orders the backends by platform, and Windows x64 is a validated platform in the runtime card. Robustness: environment variable names are resolved case-insensitively (`platform.environment_view`/`merged_environment`; `astap_cli.exe` under `Program Files` was invisible before), a run refuses up front with `OUTPUT_PATH_TOO_LONG` when its deepest staging path would exceed the process's path limit (`openastroflow_engine.path_budget`, `hardware.pathLimit`; staging names shortened), file removals and renames retry through antivirus sharing violations (`platform.remove_file`/`remove_tree`/`rename_with_retry`), worker stdio is UTF-8 regardless of the console code page, Windows on ARM64 is refused with `PLATFORM_UNSUPPORTED`, quality-control and registration workers are bounded by free memory (`tuning.qcWorkers`, `tuning.availableMemoryBytes`), FITS bands are read with buffered `readinto` on Windows (byte-identical; `LIGHTFRAMEQC_FITS_READER` overrides), and one worker pool serves screening, analysis and registration. Desktop: the Windows release executable is a GUI-subsystem binary (no console window opens next to the app), every sidecar runs inside a Job Object with kill-on-close (cancel and quit terminate the whole tree), progress streams survive invalid bytes, previews travel as bounded data URLs so outputs on other drives show them, the chip name comes from `cpuid`. Packaging: the native DLL and the desktop executable link the C runtime statically and `scripts/pe_imports.py` proves it (`build_native_runtime.py --require-static-crt`, Windows bundle attestation of every DLL/PYD/EXE import), the installers embed the WebView2 bootstrapper, the release workflow installs the MSI on the runner, attests it and uninstalls it, and the prerelease notes cover SmartScreen.
- Deterministic source extraction on Windows. SEP 1.4.1's deblending draws from an unseeded `rand()` on MSVC and its Lutz/deblend buffers are uninitialised, so two runs of one project differed by a star and therefore in the masters. Windows builds use `sep 1.4.1+oaf.1` ([packaging/patches](packaging/patches), `scripts/build_sep_wheel.py` from the hash-pinned sdist; behaviour-neutral where the PyPI build was deterministic), every receipt records a determinism self-test (`execution.sourceExtraction`, doctor `sourceExtraction`) and warns `SEP_NONDETERMINISTIC` otherwise; `lightframeqc.source_extraction`.
- Deterministic Lanczos-3 weight table (registration kernel v3, `normalized-lanczos-3-domain-union-support-clamp-v3-table2048`). The six tap weights of a sub-pixel fraction are read from a 2048-interval table with cubic Lagrange interpolation; the nodes are computed by the module's own Taylor series in a fixed Float64 order (`openastroflow_engine.lanczos_table`, `engine/native/src/Lanczos3Table.cpp`), never from the host's libm, so every platform and library version builds the same table (`oaf_native_lanczos3_table_v1` hands the native table to the identity test) and the native kernel and the NumPy reference stay value-identical. Interpolation error < 1e-12 against the exact weights (four orders of magnitude under Float32 resolution). This replaces six transcendental calls and 48 divisions per output pixel: a rotated 26 MP warp 2.02 s → 1.35 s on one core, the fused calibrate+warp stage 19.6 s → 15.1 s, the 61-frame NGC 7331 project 82.0 s → 76.2 s. It is a change of the numerical evaluation, so the masters are no longer bit-identical to kernel v2's: [`tools/validation/master_tolerance_gate.py`](tools/validation/master_tolerance_gate.py) states and checks what such a change may do (identical NaN masks; ≥ 99.99 % of pixels within 16 ulps or 0.002 σ — the robust statistics of the normalization jump by one order statistic when a registered pixel moves by a unit in the last place, shifting tiles by ~1e-3 of the noise; ≤ 1e-6 of the pixels outside that bulk, each within 2 σ — rejection decisions at the clip boundary that flip; accepted-sample counts within 0.01 %; identical per-metric `evaluate_masters.py` statuses and its SNR gains and depth within 0.002 — the per-filter label is reported, and a label that flips while the statuses and numbers are unchanged is the label rule's hard threshold crossed by a rounding, not a change of the master). On NGC 7331: 99.99998–100 % of pixels in the bulk, p99.99 |Δ| ≤ 6e-3 ADU (σ ≈ 3.3–5.4 ADU), 1–5 outlier pixels per master (max 1.22 σ), accepted counts equal, all 124 per-metric statuses identical, G_4/G_8/Δm shifts ≤ 1e-4 (R's G_8 1.019993 → 1.020002 crosses the evaluator's `|G_8 − 1| ≤ 0.02` equivalence threshold, so its label reads INCONCLUSIVE instead of EQUIVALENT).
- The global normalization of the next filter group is fitted on a helper thread (a third of the cores) while the current group integrates; the fit is a pure function of the group's frames, hints and transforms, so the coefficients are identical (`normalizationPrefetched` in the group timing). About −1 s on the 61-frame project; the fits are CPU-bound, so the overlap is limited to the integration's I/O and Python phases.
- [`benchmarks/trace_run.py`](benchmarks/trace_run.py): a tracer for real runs (`--profile <timer>` samples a timer's calls under cProfile; the trace is written even when the run fails). It executes any engine CLI command in-process with timers around the stages, the native kernels, the FITS/XISF I/O and the numerical steps (the spawned worker processes install the same timers through the `spawn` start method and hand their events back), samples CPU utilisation and resident memory, and writes a Chrome trace-event file for Perfetto plus a per-stage / per-timer summary (wall, CPU of the process and its children, cores busy; inclusive and exclusive time, calls, mean, maximum).
- Native bilinear debayer (`oaf_native_cpu_debayer_bilinear_v1`), value-identical to the NumPy reference `lightframeqc.cfa.bilinear_debayer`, which now calls it through an accelerator hook when the engine's native library is loaded: 29 ms instead of 1.25 s per 26 MP mosaic, so a one-shot-colour Light costs its three warps and little else in the fused stage (the synthetic 26-frame RGGB project run: 110 s → 79 s).
- One-shot-colour (Bayer / OSC) input ([recipe](docs/recipes/osc-cfa.md)). A Light with a known Bayer pattern (`RGGB`, `BGGR`, `GRBG`, `GBRG`; header `BAYERPAT`/`CFAPAT` or PixInsight's `PCL:CFASourcePattern`, or a hash-bound confirmation) is processed instead of blocked: screening and registration measure a luminance (block-mean previews use an even block size on mosaics, `lightframeqc.native_psf` stamps and the registration's full-resolution refinement read a bilinear-debayered luminance, so centroids and star shapes are the sensor's, in mosaic coordinates); calibration stays in the mosaic domain with **separate flat scaling factors per colour channel** (`FrameExpression.pattern_scales`: each Bayer channel is divided by the master flat normalized to its own channel median, as PixInsight's "separate CFA flat scaling factors") and same-colour hot-pixel replacement; the calibrated mosaic is debayered (`lightframeqc.cfa.bilinear_debayer`, banded, band-invariant) into R/G/B planes that are registered into three **colour channel groups** named `R`, `G`, `B`, which the rest of the pipeline — normalization, rejection, weights, region maps, shared crop, masters (`OAFCFA`/`OAFCFACH`/`OAFCFAF`), solve, colour product — treats exactly like filter groups; the project layer expands a Bayer Light set into its target's `R`, `G`, `B` panels. With drizzle the channel groups are **Bayer-drizzled**: the calibrated mosaics' own samples of each colour are dropped with the group's normalization, weights and rejection (`DrizzleGroupRequest.channel`, receipt `recipe.cfaChannel`, header `OAFDRZCH`). Masters built by a run inherit `BAYERPAT`; masters must share the Lights' pattern; a Bayer set cannot share a target with mono `R`/`G`/`B` filters (`CFA_CHANNEL_FILTER_COLLISION`). The desktop admits Bayer frames with an explanatory note and its raw-frame confirmation accepts the four patterns. Validation on a synthetic RGGB set built from the 26 real NGC 7331 mono L Lights (channel gains 0.80/1.00/0.65, tinted flat): channel skies equal the mono master times the gains; 1× debayered channels keep 97–99 % of the 4-px star flux with 5–10 % wider stars; the 2× Bayer drizzle recovers 99.5 % of the flux with stars 3 % sharper than the mono Lanczos-3 master. No real OSC data set has been processed yet.
- Native drizzle integration (`oaf_native_cpu_drizzle_v1`, [`openastroflow_engine.drizzle_native`](packages/engine/src/ufwbpp/drizzle_native.py)) replaces the STScI-based executor. The drizzle of a filter group is a second integration of exactly what the ordinary integration used — the calibrated unregistered Lights, their full-resolution registration matrices, the global-normalization scale/offset/offset grid applied in the same Float32 arithmetic at the registered position, the integration weights (noise, selection and region weight maps) and the per-sample rejection decisions (the accepted-sample masks are recorded by a tile observer during the ordinary integration and sampled at each pixel's registered position, as PixInsight's DrizzleIntegration reads ImageIntegration's rejection maps) — on a `scale` times finer grid. Scales 1–4, drop shrink 0.1–1, square (exact quadrilateral clipping), circular (exact disc area), Gaussian (FWHM = drop width) and point kernels, optional Bayer drizzle into three colour planes (`RGGB`/`BGGR`/`GRBG`/`GBRG`). Output rows are split across threads and every thread visits the input pixels whose drops can touch its rows in row-major order, so the result never depends on the thread count or the band split; each drop is located by the inverse map of the band and the monotone row mapping. Products are one multi-extension FITS per filter (`SCI`, `WHT`, `COVERAGE`) with `OAFDRZ*` header cards and a content-hashed receipt (inputs, transforms, normalization and mask provenance, dither phases, coverage/weight percentiles, timing). The recipe gains `drizzle.kernel`; the CLI `--drizzle-kernel`; the desktop's advanced options offer scale, kernel and drop shrink. Drizzled masters share their grid by construction, so the same-grid solve unification now covers them (tolerances in native pixels, scaled by the drizzle scale). Sampling, dither and coverage evidence is recorded as advisory instead of blocking. NGC 7331 (61 × 26 MP Lights, M3 Pro): 0.68 s per frame at 2×, 50 s for four filters, 178 s for the whole project (97 s without drizzle); against the Lanczos-3 master in native units the half-light radius is 2.5–4.4 % smaller, the effective noise over 4 × 4 native pixels 6–7 % lower, star flux 0.993–0.994 of the ordinary master, coverage 99.95–100 %.
- Desktop: the window is redesigned as one project document in the macOS idiom: a toolbar with import actions and the run's activity, a source-list sidebar (project states, sources by target and filter, results), a content area with the frame table, the screening table with decision filters and the target × filter matrix, the processing stages and the result masters, an inspector for the selected frame's evidence, and a bottom launch bar. Light and dark follow the system; a new brand mark and application icon (generated by `apps/desktop/scripts/brand_icon.py`). The workflow state machine, the engine bridge and the accessibility contract are unchanged.


- Unattended Light selection behind `selection.policy` (`legacy-gate` stays the default and reproduces the historical admission exactly; `unattended-v1` decides every Light from the quality-gate evidence without a review gate: hard guards exclude unusable frames, "insufficient evidence" REVIEW codes keep the frame at reduced weight, defect REVIEW codes and the multi-family cloud code enter a gray zone at reduced weight, a PSF cut-off and a `(FWHM / group median)^(-2p)` weight factor follow the priority (depth, balanced, resolution) for every frame, and the transparency guard is relative to the group's clear-frame median; `include-all` is a diagnostic policy). An admitted frame's registration quality weight is scaled by its confidence and PSF factor. During ordinary integration a tile observer accumulates a leave-one-out counterfactual for every frame (8x8 block-level weighted means on 64-row statistics tiles: block-noise depth, second-order background residual, weighted FWHM proxy, tile-bootstrap intervals) and writes it next to each decision in `qc/selection.json`. A frame the counterfactual confirms harmful (enough tiles, interval beyond the threshold, an outlier against its group; under resolution priority also a PSF-broadening outlier) is removed and its group integrated again, up to three passes and within the soft-exclusion guard, keeping normalization references and the two-Light panel minimum; `reintegration` records what was removed and why others were kept. Large occluded regions (at least 15% of the field) are excluded softly until region weight maps exist. Light Frame QC now measures the native-resolution PSF of the brightest stars (`lightframeqc.native_psf`: half-flux radius, FWHM, wing fraction; scaled 16-bit FITS and XISF Lights are read stamp by stamp without decoding the frame) and the selection prefers it over the preview FWHM. With `selection.regionWeights` a frame whose QC grid shows a blocked or dimmed region gets a per-frame region weight map (`openastroflow_engine.selection.region`): blanked cells with a one-cell margin, transparency-loss cells reduced, a soft edge of about one cell; the ordinary weighted mean multiplies the frame weight by the map at every sample (native masked-mean V2 or the NumPy reference, value-identical), the coverage map becomes the effective weight fraction, the counterfactual weights its block sums the same way, and the receipts record the maps. A mapped frame keeps its clean area at full weight instead of being excluded for the region, unless the map blanks more than half of the field; the map's dimming term uses the QC consensus residual and only coherent patches, each map is resampled from the QC reference frame into the pixel pipeline's registered frame (the two can differ by a meridian flip), and a mapped frame's noise weight is estimated outside the blanked area. The counterfactual removes a frame for background structure only when the frame does not measurably deepen the master, and only for structure above a quarter of the block noise. Region weight maps are on by default for the unattended policies (`selection.regionWeights`). Uniform transparency evidence that normalization models (a dim night, mild extra extinction) no longer reduces a frame's confidence under the unattended policy; the guards bound it and the noise weight scales with it. Recipes accept a `selection` block and receipts record the policy. The masked weighted mean kernel gained a V2 entry with optional per-sample weights (region weight maps) that is value-identical to the NumPy reduction; without sample weights the V1 arithmetic is unchanged. Benchmarks: `selection_oracle_report.py` (gate vs oracle confusion matrix) and `selection_defect_injection.py` (synthetic defects on real Lights).
- Platform service layer [`openastroflow_engine.platform`](packages/engine/src/ufwbpp/platform/__init__.py): the one place that knows operating-system differences (`darwin`, `windows`, `linux` services behind one `PlatformServices` protocol). It reports physical/available memory (`sysconf` on POSIX, `GlobalMemoryStatusEx` on Windows), the CPU topology (`sysctl` performance/efficiency levels on Apple silicon, `GetLogicalProcessorInformationEx` physical cores/SMT/hybrid `EfficiencyClass` on Windows, `/proc/cpuinfo` on Linux), the native library file name, and every probe is a pure function of its raw input so each platform's parser is tested on every host. `HardwareProfile` now carries `platformId`, logical/physical/performance/efficiency cores, SMT, ISA features, the measured memory and the source of each fact, and the `doctor` command, execution plans and pipeline receipts (`platform.hardware`, `platform.tuning`, `platform.nativeKernels`) record them.
- Native CPU feature probe `oaf_native_cpu_features_v1` (cpuid + XSAVE state on x86-64, `neon` on arm64) with the library's SHA-256 exposed as `native_kernels.describe_native_kernels()`; receipts and `doctor --json` show which library ran and which instruction sets the machine offers. No kernel selects code by these facts.
- [`scripts/build_native_runtime.py`](scripts/build_native_runtime.py): one cross-platform Release build → `ctest` → install chain for the native kernels (MSVC `/W4 /WX /fp:strict` on Windows, Metal on macOS), with a JSON report of the compiler and the installed library digest. The Python CI job now builds and installs the kernels on Ubuntu, macOS and Windows before the tests, so the value-identical differential tests run against the real DLL on Windows, and both the CI smoke and the sidecar builder fail closed when the frozen worker cannot load the native library (`NATIVE_KERNELS_MISSING`; `--allow-missing-native-kernels` for development builds). On Windows the DLL is collected as a PyInstaller binary so the MSVC runtime it links (`msvcp140.dll`, `vcruntime140*.dll`) ships inside the sidecar.
- The platform service layer also owns the file-system and process primitives that were duplicated across modules: the create-only directory rename (`renamex_np` on macOS, `renameat2` on Linux, `MoveFileExW` without replace on Windows; `NoReplaceError` carries `OUTPUT_EXISTS` with the pre-check/race distinction so `e2e`, `pixel_pipeline` and `color_product` keep their exact error codes and messages), the directory fsync (`FlushFileBuffers` on a backup-semantics directory handle on Windows, previously a no-op there), the create-only file publication (`os.link` + unlink; on Windows a volume without hard links falls back to a no-replace `MoveFileExW`), volume facts (`mount`, `/proc/mounts`, `GetVolumeInformationW`: file system, hard-link support, case sensitivity), the cache/data roots, the child-process isolation options and process-tree kill used by the solver runtime (`taskkill /T` on Windows), the well-known install locations of ASTAP/solve-field/siril-cli, and `keep_awake()` (`caffeinate -i` on macOS, `SetThreadExecutionState(ES_SYSTEM_REQUIRED)` on Windows) which the `run`/`run-project` commands now hold for the duration of a run. Six `_fsync_directory`, three no-replace renames, two root selectors and three executable tables collapsed into one implementation each; the macOS project run stays bit-identical.
- [`scripts/windows/bootstrap.ps1`](scripts/windows/bootstrap.ps1): idempotent winget bootstrap of a Windows x86-64 build machine (Python 3.12, CMake, Ninja, VS 2022 Build Tools with the C++ workload, uv) that records every installed tool in a JSON report.
- [`tools/validation/evaluate_masters.py`](tools/validation/evaluate_masters.py) and [`docs/master-evaluation-standard.md`](docs/master-evaluation-standard.md): a quantitative standard for judging a master against the PixInsight WBPP master of the same data. One matched clean-star list on both native grids, a photometric model `P = a*O + b`, and PASS/WARN/FAIL per metric with bootstrap confidence intervals: PSF (half-light and windowed-moment FWHM, ellipticity, core concentration), noise (binned effective noise gain `G_b`, empty-aperture depth, faint-star flux preservation), background flatness in units of PixInsight's own noise (high-order residual, axis-aligned power, edge roll-off, auto-STF zone spread and visible-structure fraction), artefacts (core clipping, hot/cold pixels, trail residuals, ringing, borders), photometry (linearity, per-bin flux ratio, saturation, flux-ratio field) and cross-channel alignment; per-filter and run verdicts (BETTER / EQUIVALENT / WORSE / INCONCLUSIVE).

### Fixed

- A uniformly moonlit night passed the legacy gate and put a gradient into the luminance master. On the six-night NGC 6822 campaign (97 Lights; L 44 from three nights: 18 on a dark night, 23 on a moonlit night, 3 on a night with a changing sky) the moonlit frames had a raw sky 1.9–2.4× the dark night's, 52–58 % of its detected stars and 0.22–0.34 mag of extinction, yet the gate admitted 19 of the 23 because its nightly-relative model sees a self-consistent night as normal; with 39 L frames integrated the moonlit night carried about a quarter of the master's weight and the luminance master measured a quadratic background span of 6.80 σ of the per-pixel sky noise (corner spread 6.07 σ; 64-pixel box medians, galaxy and borders excluded). The same pipeline on the 17 L frames the maintainer had blinked by hand measures 3.28 σ / 4.59 σ, PixInsight WBPP on the same frames (LocalNormalization on) 3.96 σ / 5.36 σ, and the R/G/B masters agree with PixInsight's within 0.3–0.9 σ; a flat check against PixInsight's calibrated frame agreed to one global factor (0.99490) with a 0.6 ADU box-median difference span, so calibration, normalization and integration were not the cause. The blink flags (above) pre-drop all 23 moonlit frames through the combined sky-and-sources rule and no dark-night frame; the legacy gate is unchanged in this respect and the [legacy-gate page](docs/recipes/automatic-screening.md) states the limit. Frames carrying a blink flag no longer anchor a filter group as its registration or normalization reference: the previous lowest-sky preference picked cloud-dimmed frames whose background the master inherited (flag defaults alone: 6.8 σ → 2.3 σ large-scale structure on that luminance master; reference project evaluated, all families PASS/WARN as before).
- Quality gate: nightly z-scores on nights of one to three frames were unstable (background z of 25.3 and −12.8, noise z of −47 on the same campaign) because the peer spread of a tiny night is a few counts. The z-score scale is now at least 2 % of the night's centre, and a night with fewer than five peers also uses at least the whole cohort's spread (−12.8 → −0.9, 25.3 → 2.1). This changes gate evidence, so `GatePolicy.evidence_revision` is 4: REVIEW approvals recorded under revision 3 are invalid and must be made again. The blink flags never use these z-scores.
- REVIEW approvals for projects with several targets or filters. The desktop sends the reviewer's selections (Light digest + gate-policy digest) unchanged; `run_project_e2e` binds them to the target run that owns each Light, against that run's own request (its Lights, the shared masters it uses, the gate policy, the pipeline parameters), which `run_e2e` re-verifies as before. A selection that names no current Light, or names one twice, is refused before any work (`REVIEW_APPROVAL_SOURCE_AMBIGUOUS`). The single-panel restriction (`PROJECT_REVIEW_APPROVAL_SCOPE_UNSUPPORTED`) now applies only to pre-bound approvals. On a six-night L/R/G/B campaign the reviewer could not admit a single one of 68 reviewed frames before.
- Desktop: the launch bar says what the run will leave out before it starts — a project that has not been screened is told that the run screens on its own and excludes REVIEW frames without asking (with a button to screen first); a screened project shows how many REVIEW frames will not be stacked, with "Approve all N REVIEW" and a link to the review page. The review page has approve-all / withdraw-all buttons, and the result page states "N of M frames stacked" in its headline metrics.
- Quality gate: the raw detection count is compared with the reference frame only when both were taken on the same night. Against a reference from a darker night it measures the sky brightness (moon, twilight, haze), not the frame: every frame of a clear moonlit night was reviewed for "source retention" although its transparency and bright-star completeness were normal. Within-night drops still use the night's own high envelope.
- Registration never anchors on a manually admitted REVIEW frame while gate-passed frames exist (`run_registration(reference_candidates=…)`). The reference score rewards many sharp detections, which a cloud-covered frame fakes with sub-pixel noise blobs; one such approved frame became the reference and left every real frame unregistered.
- A REVIEW frame that had no transform in the quality pass (cloud, no stars) is reported as `registrable: false` by the preflight, cannot be approved in the desktop ("Cannot be registered; stays excluded", skipped by approve-all), and is refused by the engine (`REVIEW_APPROVAL_UNREGISTRABLE`) instead of failing the whole run at registration.
- Quality gate: the nightly extinction fit no longer lets cloud excursions define the airmass slope. Same-night pairs with |slope| > 2 mag/airmass (a cloud inside a night with a small airmass span gives tens of magnitudes per airmass) are discarded before the Theil-Sen median, the median is clamped to the physical 0–1 mag/airmass range (`SLOPE_OUT_OF_RANGE` marks the fit unreliable), and the night zero-point rule (`GATE_NIGHT_ZEROPOINT_SHIFT_REVIEW`) only fires on a reliable fit, like the other extinction rules. On a six-night L/R/G/B campaign the fit had produced slopes of 6–14 mag/airmass and nightly offsets of 0.6–3.6 mag, so every night except the reference night was reviewed as "dimmer" and the R/G/B masters were built from 3 frames each; with the fix 52 of 97 frames pass instead of 26 and the remaining reviews are genuine (cloud, low source retention).
- The plate solver's process `PATH` now starts with the solver's own directories (the invocation directory and the resolved symlink target). `solve-field` runs its helpers (`image2pnm`, netpbm's `pnmfile`, `astrometry-engine`) through `/bin/sh` and looks them up on `PATH`; the desktop application launched from the Finder inherits launchd's minimal `PATH` without `/opt/homebrew/bin`, so every solve from the GUI failed within a second (`pnmfile: command not found`, exit 255, `ASTROMETRY_REQUIRED`) while the same project solved from a terminal. The environment is otherwise still the restricted solver environment.
- Desktop: a run that fails closed no longer keeps the current stage spinning at "Publication and desktop verification". The stage that was running is marked failed, and a failure card (title, failure code and message, the stage it stopped in, and the `<output>.unsolved` evidence directory) replaces the one-line error text; the result-gate failure path does the same.
- Desktop: the frame inventory groups frames by channel — role, target, filter and sensor geometry (binning, dimensions, CFA pattern) — instead of splitting a filter into one row per night and per 0.1 °C of sensor temperature. Exposure, temperature, gain/offset, readout mode and capture dates are shown as ranges within the row (with the number of nights).
- The desktop's sidecar launcher retries for up to a second when the executable is momentarily "text busy" (`ETXTBSY`): on Linux a fork elsewhere in the process — another launch, a test thread — holds a just-installed executable's write handle until its own exec, and the CI's `fake_sidecar_progress_is_streamed_before_completion` test failed on that race. rustc, cargo and git retry the same way; every other launch error is still reported at once.
- `lightframeqc.content_hash` no longer caches the digest of a file whose mtime is younger than two seconds: on Windows file times advance in clock ticks and `st_ctime` is the creation time, so a same-size rewrite in the same tick kept the stat identity and returned the previous digest (the Windows CI job caught it in `test_rewritten_file_is_hashed_again`). A run's sources are old files and stay cached; its own products are hashed by their writers or once more when verified (about a second per run).

### Changed

- The normalization offset grid is added to a band of integration rows in one broadcast instead of a Python loop over the rows (`_add_offset_grid_rows`). The elementwise Float64 arithmetic is unchanged, so the masters are bit-identical; the loop's thousands of small NumPy calls per band had been fighting twelve threads for the GIL while the native kernels ran (150 s of thread-wall on the 61-frame project for about 4 s of arithmetic). The registration's member estimation (bridge and direct RANSAC) and full-resolution refinement run in the stage's spawned worker pool — the same pool that analysed the frames, closed when the stage ends — instead of GIL-bound threads; workers receive the star catalogs and decode the full-resolution frames themselves (the reference once per worker), and the preview warp check stays in the main process, so every transform and the masters are unchanged (`register_analyses` 8.1 s → 3.8 s). The project's final products and the panel's artifact records are hashed concurrently before the receipts are written. Together: the 61-frame NGC 7331 project run drops from 95.7 s to 82.0 s with hash-identical masters.
- The 61-frame NGC 7331 project run on the M3 Pro dropped from 170 s to 97 s with bit-identical masters (the four solved masters hash the same as a build of the previous commit on the same machine; the platform-independent code paths and the native kernel, which builds under the same MSVC `/W4 /WX /fp:strict` flags, are shared by macOS and Windows), by moving hot spots out of Python and cutting whole-frame passes:
  - Transient-trail detection: the dyadic fast Radon transform, the per-level z standardisation and the (1, 5, 7) peak search of every frame run in a native kernel (`oaf_native_cpu_radon_peaks_v1`, receipt `lineKernel: native-cpu-radon-peaks-v1`) that keeps only the lines that can touch the image and the two live dyadic levels instead of ten dense levels of `take_along_axis`; the NumPy reference stays as the fallback (`numpy-radon-peaks-v1`) and the differential tests require identical candidates. About 1.7 s → 0.12 s per frame; a 13-frame group's detection went from 4.9 s to 1.0 s.
  - Corridor rejection and the trail background correction evaluate only the pixels a corridor can contain (the analytic per-row interval with a two-pixel margin, then the exact per-pixel test) and the background model only at the pixels whose acceptance changed, with the frame sums accumulated in the same order as the whole-tile evaluation; the L group's rejection phase no longer spends 7 s on ten trails' whole-tile masks.
  - The rejection kernel pools the row-window MADs through a sorted sliding window instead of selecting every pixel's window median anew, and sorts a pixel's short sample once (insertion sort, deviations merged from the sorted sample) for the median and the MAD; the same order statistics, about 40% less time per tile.
  - Global normalization: the sky-response lattice of each tile row is evaluated once per group (it is the same for every frame) with a separable bilinear evaluation, each frame's tile samples are gathered per band instead of per tile, the per-frame tile backgrounds sort each tile once and take the quantiles and the median of the kept run from the sorted tile, and the native tile-offset kernel selects its medians without sorting. 4.9 s → 1.7 s per 13-frame group.
  - Registration: frame analysis (preview, calibration, SEP detection, which holds the GIL) runs in spawned worker processes like the screening stage; the filter groups' transform trees, the preview warp checks, the normalization-reference flatness and the stellar-scale photometry run concurrently, the photometry inputs are prepared once per frame, and the tile backgrounds of the flatness measure are vectorised. 25 s → 14 s for 61 frames.
  - Auto-crop finds each frame's valid run per row by bisection on the exact per-pixel test instead of evaluating every pixel of every frame (4.2 s → 0.2 s); the block-mean previews and the transient block means reduce whole bands at once; the frames of an integration band are read concurrently; the four filters solve concurrently (17 s → 7 s).
  - The M3 Pro tuning row uses twelve Lights in flight and twelve kernel threads (see `docs/hardware.md`).
  Integration receipts record the phase times (`execution.timingSeconds`) and the pixel-pipeline receipt the stage times (`statistics.timingSeconds`).
- One step from import to result. The desktop's import page now carries the output folder (remembered between sessions), the advanced options and the start button; the separate Review and Process pages are gone. Screening runs inside the job as before, and the result page lists every Light the gate excluded with its disposition, the gate's reasons and a small preview (`execution.screening` in the project receipt, `qualityControl.screening` and `qc/review/*.png` in each run; the desktop reads them through the completion event). The screening review stays available as an optional button on the import page for inspecting and approving REVIEW frames before a run. Before a screening, a panel only needs two Lights to be startable; the run enforces two admitted Lights per panel as before.
- Light screening is 2-3x faster: frame measurement and per-frame group analysis (registration, spatial features) run in spawned worker processes instead of GIL-bound threads (`lightframeqc.parallel`, chosen for 12 or more frames, with a thread fallback when a pool cannot start; every frame runs the same function, so values are unchanged), the spatial-feature footprint test builds each frame's inverse transform once instead of inverting the matrix per star, and the group-analysis cache key hashes the star lists as binary arrays instead of 88 MB of JSON. On the 67-frame NGC 7331 set the desktop screening went from 22 s to 10 s (measurement 18 s to 5 s, analysis 8.5 s to 3.5 s uncached and 1.8 s to 0.4 s cached); the run's quality-control stage gains the same.
- The worker starts three times faster for the desktop's short commands (`inventory`, `calibration-check`, `doctor`, `catalog`): the package root and the CLI import the E2E pipeline, the solver backends and the quality-gate analysis stack only for the commands that run them (1.2 s to 0.35 s per launch), so a dropped folder shows its frames and calibration check in about a second. The desktop also subscribes only to the drop event instead of every drag-over event.
- Project output reads at a glance. The desktop names the result directory `<target>_<YYYY-MM-DD>_<HHMM>` (`NGC7331_2026-09-18_2335`; a mosaic's panels contribute the words they share, unrelated targets are joined, a `_2` counter avoids collisions) instead of `ultra-fast-wbpp-project-<ms>-<n>`. The published directory holds one solved master per channel named after it (`L.fits`, `R.fits`, `G.fits`, `B.fits`), the color cube (`LRGB.fits`, or `RGB.fits` without L), `previews/` (`L.png` … `LRGB.png`, `LRGB.tiff`) and `receipt.json`; PixInsight labels an opened image with its file stem, so the channels open as the views `L`, `R`, `G`, `B`. Every intermediate stage (`shared-calibration/`, `runs/<target>/`, `mosaics/`, `color/`) moved under `details/`. A channel whose grid is final is the run master itself, hard-linked rather than copied (the former copy also stamped `OAFALGN`/`OAFWCSPR` into its header; that provenance is now `execution.alignment.<key>.referenceFilter`/`wcsProvenance`, and `publication` records `HARDLINK`, `COPY` or `CROPPED_COPY`), which saves one full set of masters per run. `ColorProductRequest.product_name` names the color files (default `RGB`/`LRGB`, formerly `linear-rgb.fits` and `preview-16bit.*`).
- Pixel rejection scale model v2 (`row-pooled-mad-frame-studentized-v2`, native kernel `native-cpu-mad-rejection-v2`, NumPy reference `numpy-nanmedian-pooled-mad-v2`). The per-pixel MAD of an N-frame stack has a relative error of about 1.2/sqrt(N); at N = 11-13 the pixels where it came out low clipped about 1% of their *good* sky samples (the RGB masters of the NGC 7331 run rejected 1.6-1.7% of star-free background samples against 0.59% for the 26-frame L master), which costs 2-3% of the master's SNR in a Monte Carlo of pure Gaussian stacks. The noise part of every pixel's scale is now the median of the per-pixel MADs over the 25 pixels of its row window (25 N samples), each frame whose per-pixel noise exceeds the group's sampled mixture scale is compared against its own noise (factor `sigma_j / sampledSigmaMedian`, never below 1), and the excess per-pixel variance beyond the pooled noise (star cores under variable seeing) is kept per pixel. By construction the new threshold is never tighter than the v1 per-pixel threshold, so v2 rejects a subset of the v1 samples; hot pixels, cosmic rays and trails stay far beyond either. `IntegrationParameters.rejection_pool_half_width` (12) and `rejection_frame_noise_scaling` (on) select the model; 0/off restores the v1 decisions bit for bit, and receipts record the scale model (`rejectionMask.sigmaFloor.scaleModel`, `rejectionMask.frameScaleModel`). The native kernel and the NumPy reference stay value-identical under the differential tests; the kernel costs about one extra second per 26 MP filter.
- Transient trail detection v2 (`temporal-residual-radon-line-corridor-v2`): each frame's residual against the temporal median is integrated along every line of every dyadic length with a fast Radon transform (the multi-scale streak detection of Nir, Zackay & Ofek 2018), so a satellite is found from the sum of its whole length instead of from individual bright samples; the v1 detector needed samples above 2.5 sigma per bin and six of eight supported segments, which missed a 0.5 sigma-per-pixel trail across the whole G frame of the NGC 7331 run and any trail that fades along its length. Candidates are refined on the preview, their extent is tracked outward along the line while the running mean stays positive (bridging blinking gaps), and a line is kept only when it is significant, distributed, narrow (the three core bands hold most of the positive cross-track flux) and not centred on a bright star; bright extended objects and star halos are masked from detection, and accepted corridors are blanked before the next candidate is measured. Corridor rejection itself is unchanged: only that frame's samples inside the corridor are dropped, so no real signal is lost, and the corridor now never widens beyond the profile's measured wings. On the NGC 7331 run the residual of the faint G trail in the master dropped from +0.45 (ours) / +0.36 (PixInsight) to +0.15 binned sigma; the bright trails, which PixInsight's Winsorized clipping leaves as +0.1 to +0.6 sigma wings, stay at zero. About 0.3 s per 26 MP frame.
- Integration noise weights come from the noise of 4x4 block means (`block-mean-effective-noise-v2`) instead of per-pixel noise. On a registered frame the per-pixel noise depends on the sub-pixel phase of its Lanczos-3 resampling (the kernel's sum of squared weights is 0.62-1.0 in two dimensions), so per-pixel `1/sigma^2` weighted frames by their dither phase, about 0.8% of SNR; block means recover the low-frequency noise the integration averages to within 2-3% at every phase. The same sampling pass still measures the per-pixel noise (it feeds the rejection frame factors), reads the same number of rows as before, and falls back to the plain sample dispersion on images too small for blocks; receipts record both estimates (`execution.noiseWeights`).
- Execution tuning is a table keyed by platform, CPU family, memory band and core count (`performance_profile.py`), and it separates the memory-bound number of Lights in flight (`cpuWorkers`) from the native-kernel thread budget (`kernelThreads`): the fused warp shares the budget among its in-flight Lights and integration tiles use all of it. On x86-64 the budget is every logical core (SMT siblings and efficiency cores included, balanced by the kernels' dynamic chunking) while workers stay memory-bound, so a 16 GiB/16-thread laptop registers with 4 workers x 4 threads instead of 4 x 1; the M3 Pro row keeps its validated 8 threads and the generic Apple silicon rows keep the previous `cpuWorkers` budget. Windows and Linux x86-64 hosts share `CpuFamily.X86_64` and the `windows-x86-64-cpu-v1` / `linux-x86-64-cpu-v1` rows (2/4/4/8 workers below 12/16/24 GiB and above); the Apple silicon and M3 Pro rows are unchanged and the M3 Pro tuning values are identical to before. The physical-memory probe no longer returns a fixed 8 GiB on Windows: the platform service layer measures it, and the 8 GiB value survives only as an explicit `fallback` that receipts name when every probe failed.
- The native kernels' `ParallelRange` claims fixed-size chunks (8 warp rows, 4096 rejection pixels, 8192 reduction pixels, one normalization tile) from an atomic counter instead of splitting a range statically per thread, and the calling thread drains chunks too. Per-item results are unchanged (thread-count invariance tests cover the partial last chunk), hybrid or throttled cores no longer hold the tail of a range, and on the M3 Pro the 12-frame integration benchmark dropped from 4.76 s to 4.24 s with the warp unchanged (0.415 s → 0.404 s); the 61-frame project run stays bit-identical at 169 s.
- Every source file is hashed once per process: [`lightframeqc.content_hash`](packages/light-frame-qc/src/lightframeqc/content_hash.py) caches the SHA-256 under the file's stat identity (device, inode, size, mtime, ctime) after a descriptor-bound read, and every stage helper and the race-aware identity hasher share it. Receipts are unchanged; a project run of 61 frames dropped from 188 s to 169 s.
- Moved the ordinary pipeline's three hot loops into multithreaded native CPU kernels that reproduce the NumPy reference arithmetic value for value: the normalized domain-bounded Lanczos-3 warp, the full-stack median/MAD sigma-clipping decision, and the Float64 weighted reduction. The NumPy implementations remain the portable fallback and differential tests require identical pixels, maps, and counts from both paths; `OPENASTROFLOW_DISABLE_NATIVE_KERNELS=1` forces the NumPy path. Receipts record the kernel used per stage.
- Fused calibration and registration: each Light is calibrated in memory from once-decoded masters and warped directly, in as many concurrent workers as the registration memory budget allows, with the remaining CPU share given to each native warp. Calibrated Lights are no longer written to disk in ordinary E2E runs (`materialize_calibrated_lights`; Drizzle and the public portable pipeline still write them). Registered outputs are hashed by the streaming FITS writer instead of being reread.
- Removed the private byte copy of FITS sources and the two full rehashes of that copy from the E2E path. Sources are read in place through read-only handles, their captured stat identity is rechecked at every trust boundary, the inventory digest is handed to the pixel pipeline instead of being recomputed, and the final publication gate still rehashes every original. A source mutated mid-run is reported as `SOURCE_CHANGED`.
- Evaluated the six Lanczos-3 tap weights from three transcendental calls per axis through exact trigonometric identities (`normalized-lanczos-3-domain-union-support-clamp-v2`) in both the NumPy reference and the native kernel; the interpolation contract is unchanged and pixels differ from v1 by at most one Float32 ulp. Transform keys are matched by canonical path, generated masters, cropped masters and evidence maps take their digests from the streaming writer, and the same-filter transform estimates run concurrently.
- Moved the global-normalization per-tile offset statistics (joint quantile selection, median/MAD clipping, residual median and dispersion) into a native multithreaded kernel that reproduces NumPy's linear quantile and median arithmetic exactly, and sampled the offset grid by row bands instead of one row read per sampled row. The trail-background correction is now evaluated only on the row runs that contain additionally rejected pixels.
- Replaced the memory-mapped FITS writer with buffered sequential writes and made fsync conditional: pipeline intermediates inside the transient E2E work tree are no longer synchronously written back (the promoted products still are). `auto` ordinary integration now selects the multithreaded native CPU kernels when they are loaded (measured faster on Apple silicon than the Metal weighted-mean path, whose host-side normalization, copies and parity reruns exceed its GPU time); explicit `generic-apple-metal`/`m3-pro-tuned` requests still run the audited Metal path. Global-normalization target fits, transient-trail detection per frame, and source-file hashing now run concurrently.
- Parallelized the transient-trail preparation pass and the full-resolution registration refinement across frames, and let the generic Apple silicon profile use up to eight QC/registration workers as cores and memory permit (two below 12 GiB, four below 24 GiB). The M3 Pro profile now uses eight QC workers. The registration memory budget grows to a sixth of usable memory, capped at 4 GiB, because in-flight Lights are held decoded.
- Removed the remaining per-row and per-star Python overheads without changing any value: sampled statistics (integration statistics, the rejection sigma floor, and the global-normalization pairing) gather every sampled row of a frame in one read; the sigma-floor median/MAD statistics are evaluated for all sampled coordinates at once through an exact re-implementation of NumPy's `nanmedian` over the frame axis; spatial-transient binning reads 128-row bands; full-resolution registration refines every star's centroid from one gathered patch stack with the same Float64 arithmetic as the previous per-star loop; the residual-background cell statistics evaluate all frames of a cell at once with the same Float32 centre/MAD/clip arithmetic; the Lights of the final fused-warp submission round receive the CPU share of the idle workers (`tailNativeThreads`); write-out statistics use masked reductions instead of compacted copies; and preview PNGs use a fast deflate level (the pixels are identical to the previous optimized encoding, only the byte stream and therefore the receipt digest differ). Differential tests hold each replacement to its per-row or per-star reference.

### Fixed

- Light Frame QC measurements were not reproducible on Windows: the `sep` 1.4.1 win_amd64 wheel returns different object counts and fluxes when `sep.extract` runs concurrently in several threads (a controlled test on the laptop differed in every trial while the same test on macOS was deterministic), so QC features, quality weights and finally the masters drifted between runs of the same data. `lightframeqc.measure` now serializes the two `sep` calls behind one lock on every platform except macOS (whose build was measured deterministic and keeps the concurrent path); photometry, matching and statistics remain concurrent.
- `lightframeqc.content_hash` never cached a digest on Windows: the pathname stat reports the creation time as `st_ctime` while the descriptor stat reports the change time, so the before/after identities could not agree and every file was hashed on each request. Only size and mtime are compared across the pathname/descriptor boundary on Windows now (the rule `lightframeqc.identity` already used); the cache key itself is unchanged.
- Stopped resampling filter masters after integration. A project now runs every filter of a target in one E2E run, so all Lights register onto one reference frame and every master is cropped to the same rectangle; each master is still solved on its own, the independent solves verify the shared grid at solver precision, and the lowest-RMS solution is written to every master (`astrometry.sameGridUnification`). The final channels are then copied onto the reference grid unchanged instead of being reprojected with bilinear interpolation through independent WCS solutions, which had doubled the noise correlation, widened stars by 3% and misaligned channels by up to 0.4 px. When reprojection is still needed (mosaics), luminance is the reference and stays unresampled.
- Registration refines star positions with a Gaussian-windowed, core-weighted centroid (2 px window, `RegistrationConfig.full_centroid_window_sigma_px`) instead of a wing-weighted centre of mass: on asymmetric PSFs the centre of mass sat a night- and filter-dependent 0.1-0.2 px away from the star core and misregistered filters against each other.
- Cosmetic correction: pixels more than `cosmetic_hot_pixel_sigma` (3) robust sigmas above the master dark's median are replaced in every calibrated Light by the median of their eight neighbours before registration (`calibration.cosmetic` per frame). Unstable hot pixels leave 5-8 sigma residuals after dark subtraction, and pixel rejection could not remove them when three frames of one dither position shared a master pixel; the masters showed them as isolated bright pixels that PixInsight's CosmeticCorrection had removed.
- Integration noise weights estimate a frame's noise from the dispersion of neighbouring lattice samples along each row instead of the dispersion of all samples; a moonlit gradient had inflated the "noise" of one night's frames six-fold and effectively dropped them from the RGB stacks.
- Normalization now targets the frame with the flattest large-scale background of acceptable quality (with a small preference for a low sky) instead of the highest-quality frame (`referenceSelection` in the registration hints), and the additive offset grid is gated against its own tile measurement noise instead of 3% of the sky, so genuine low-frequency differences of a few ADU are matched, as LocalNormalization does. Two group-level corrections are then added to every frame's grid so frame-to-frame matching is unchanged: a sky-proportional edge response (`skyResponse`, `sky-proportional-edge-response-theil-sen-sensor-frame-v2`) regresses tile backgrounds against frame sky across the group and subtracts the part that scales with the sky, in proportion to each frame's own sky, so a residual flat-field edge roll-off no longer reaches the master. The regression runs in the sensor frame: each frame's tile levels are read through its registration transform and slopes are formed only between frames of one orientation, so frames taken after a meridian flip carry the same roll-off on the same sensor edge instead of confusing the fit (in registered coordinates the flip had turned the roll-off into a bogus 6% sky-correlated tilt, and the additive grid's 896 px smoothing then smeared the roll-off difference between the two orientations into a 1% tilt of the master). When two interleaved frame halves reproduce the whole response map (many frames, a wide sky range) the lightly smoothed map is applied; otherwise only the profiles of the sensor edge bands (the outer 15% of the tile grid, tapered into the interior) are applied, and an edge is kept only when its profile is significant against the interior row/column noise, is shaped like a roll-off and is reproduced by both halves. In both cases the model must reduce the between-frame structure on the tiles it touches, tiles the object dominates are excluded, and the correction is refused beyond 5% of the sky; and a low-order target (`lowOrderTarget`, `flattest-convex-combination-of-frame-tilts-v1`) moves the master's background tilt from the reference frame's tilt to the flattest non-negative weighted mix of the frames' own tilts in the registered geometry. Nights whose gradients point in different directions (a meridian flip, the moon on the other side) cancel and a single night keeps its common tilt, so the master is never flatter than the observations allow; WBPP obtains a similar cancellation only by chance when the frames chosen for its LocalNormalization reference happen to disagree.
- Ordinary registration uses the projective model. Frames of another night or hour angle differ from the reference by perspective terms that the affine model left as a field-dependent misregistration of up to 0.5 px; the NumPy resampler and the native warp kernel (`oaf_native_cpu_warp_lanczos3_v2`) evaluate the homography with the same arithmetic value for value.
- Use standard mono/master conventions in the desktop without per-file metadata approval; preserve unrecorded values, remove zero/Light-derived defaults, and retain sparse overrides only in advanced settings. Known conflicts and required calibration dependencies remain enforced.
