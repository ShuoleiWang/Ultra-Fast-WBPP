# Astrometric solving

Ultra-Fast WBPP distinguishes an acquisition `SEED` from a verified `SOLVED` WCS. N.I.N.A. RA/Dec, focal length, pixel size, and orientation narrow the search, but they do not authorize final publication.

## Automatic N.I.N.A. hint handling

For every accepted light group, Ultra-Fast WBPP computes the expected horizontal field width from the actual image width and the N.I.N.A./FITS optical metadata:

`FOV = 2 × atan((widthPixels × effectivePixelSizeMicrons / 1000) / (2 × focalLengthMm))`

`FOCALLEN`/`FOCAL`/`FOCALLENGTH` and `XPIXSZ`/`YPIXSZ` (with the `PIXSIZE*` fallbacks) are supported. The result is calculated for each light and reduced to a robust median. The recorded assumption is that `XPIXSZ` and `YPIXSZ` describe the effective pixels of the stored, possibly binned image. Acquisition RA/Dec values are also reduced to a circular sky-coordinate consensus.

An explicit GUI/CLI hint is compared with that acquisition evidence. A field-width ratio in `0.7–1.3` and a center within the requested search radius are considered consistent. When the field widths conflict, the frame-derived width wins, so a stale hint cannot constrain the solver to the wrong scale. When the centers conflict, the coordinates you give (`--ra/--dec`, or the request's hints) win: a header may carry a parked mount's pointing or another unit's, and you have no other way to correct it (provenance `explicit;conflicting-NINA/FITS-header-ignored`). Either way the rejected value, ratio/separation, selection and provenance are written into the E2E receipt. Header right ascension is read in the unit each keyword establishes: `OBJCTRA` as sexagesimal hours, a numeric `RA` as decimal degrees unless its comment names hours, `CRVAL1` as degrees when `CTYPE1` is a right-ascension axis.

## Bounded Astrometry.net profile

The default large-frame profile uses `--downsample 4 --objs 500 --depth 10-500 --pixel-error 2` when the longest image axis is at least 5000 pixels. It adapts to downsample 2 for 2500–4999 pixels and 1 for smaller images. These are solve-only arguments: executable discovery and capability probes remain isolated `--version` and `--help` calls. A required final solve accepts only the catalog-manager generated config covered by the same installed-set receipt as its indexes, and only when that config names the folder it is in (`CATALOG_CONFIG_RELOCATED` otherwise; `ultra-fast-wbpp catalog doctor` re-points a moved or copied folder). The config and every managed index are checked before execution; the `.match` `INDEXID` is then bound to exact index bytes, read again in full, and the snapshot is checked again before publication. An index file is hashed in full the first time a process uses it and afterwards checked by its stat identity ([offline catalogs](offline-solver-catalogs.md#3-confirm-runtime-readiness)).

The adapter is `astrometry-net-process-v5`. Each solve works in a private directory inside the run's staging tree on the output volume (`<staging>/work/solver/.solve.<8>.stage`; mosaic reference and survey solves in their own work directories), and `solve-field` gets `--temp-dir` there, so its temporaries leave with the attempt, also when it times out or the run is killed. Only an embedder that passes no `staging_directory` gets a system temporary directory.

The headless runtime discovers an app-managed config through the compatibility variable `UFWBPP_ASTROMETRY_CONFIG` (or `ASTROMETRY_NET_CONFIG`), then the standard Ultra-Fast WBPP data directories. Embedders can pass `config_path` and an immutable `AstrometryNetSolveProfile` directly. Arbitrary command strings are not accepted as a profile, and the config path is never added to probe arguments.

Use the [offline catalog recipe](offline-solver-catalogs.md) to inspect compatible scales, explicitly accept the versioned provider notice, download/resume checked artifacts, generate `astrometry.cfg`, and create an installed-set receipt. Nothing is fetched automatically by a solve.

When a center or scale hint exists, its first attempt receives 25% of the total timeout, capped at 30 seconds. If that attempt times out, exits without solving, or produces no exact solved marker, the remaining budget is used for a more conservative attempt with gentler downsampling, up to 1000 sources/depth, and no center or scale constraints. The process-group timeout is still the hard boundary; fallback does not extend the configured total budget.

For a roughly 1.11-degree field, install a user-managed Astrometry.net index set covering that scale; indexes 4107–4112 were present in the M3 Pro validation environment, and the accepted solution used index 4107. One index file does not prove complete coverage. See the [sanitized real-fixture validation](../evidence/m3-pro-astrometry-net-real-fixture-20260901.json) for the measured adapter and quality-gate result. Astrometry.net's `.match` `INDEXID` identifies a logical index; the strict adapter binds it to the installed-set identity, checked manifest, relative index filename, exact size, and SHA-256.

The strict final backends are a user-installed local Astrometry.net `solve-field` plus app-managed checked indexes, and ASTAP (`astap_cli`, with its own star database) whose solution the engine verifies against the same managed indexes: the engine detects stars on the final master, projects the index stars through ASTAP's WCS, matches them one to one and records the residuals, the matched count, the parity, the correspondence table and the byte-bound index identities exactly as the astrometry.net adapter does. The recipe thresholds apply to both; `backend: auto` prefers `solve-field` when both are present. There is no built-in solver and no online upload fallback, and without the managed index set ASTAP stays diagnostic-only.

Discovering an executable and validating its CLI options proves only that the adapter can invoke it. ASTAP still needs a star database covering the requested field and scale; Astrometry.net still needs compatible index files. Coverage becomes proven only when that specific final image produces the required solved marker, WCS artifacts, and validated receipt.

A solution receipt records backend/version, managed installed-set/manifest/index identities, correspondence identity, matched-star count, RMS pixels/arcseconds, scale, parity, center, search seed, and corner/center round-trip checks. Exact argv, absolute source/config/staging paths, and raw solver output are excluded from the shareable receipt. Set `UFWBPP_SOLVER_DIAGNOSTIC_DIR` only when local troubleshooting logs are needed; those separate JSON logs contain redacted argv/output tails and must not be attached to a shared project without review. Recipe thresholds are evaluated by the engine, and the desktop re-validates the solution receipt, rather than trusting an external process exit code. ASTAP's solution satisfies a strict required final solve only through the engine-side verification against the managed index stars described above; without the managed index set its result is diagnostic-only.

Crop, Drizzle, RGB combination, and mosaic projection change geometry. The last geometry-changing stage must therefore be followed by a new solve or by a validated propagation whose residual gate is at least as strict. A failed solve publishes nothing at the requested output. The run's receipt (state `UNSOLVED_WORKING`, `publication.kind: failure-evidence-only`), the solver evidence, the quality-control records and the previews go into the evidence directory `<output>.unsolved`; the integrated masters lived in the run's work directory, which is removed, so a new solve needs a new run. It never emits a green final-result card.

## Catalog refit of the published solution

Astrometry.net reports its solution with a SIP order of 2. A fast corrected optical train has cubic distortion that order 2 cannot follow: on a 12-inch f/4 Newtonian with a coma corrector (1.1° field, 0.65″/px), the solver's WCS of an M31 master is off from Gaia DR3 by 1.53″ median and 2.64″ at the 90th percentile.

After every filter of a run has solved (and the same-grid solve is shared), the engine refits the grid's solution on the managed catalog. It uses the TAN+SIP fit a mosaic panel uses, with the order chosen by the BIC up to 3, on the L master when there is one and otherwise on the first filter by name. The refit replaces the solver's solution only when both of these hold:

- its residual on held-out stars (two-fold cross-validation: each half of the matched stars against the fit on the other half) is at most 0.8 of the solver's residual on the same stars, and within the 2.0″ gate;
- every master of the grid passes the engine's catalog verification with it, at the run's own match threshold and RMS gate, the RMS judged without the stars the catalog misplaces (below).

That verification is then recorded as each master's accepted solve. The headers carry `OAFWCSRF` (the SIP order) and `OAFWCSRA` (the refit's catalog RMS in arcseconds); the receipt's `astrometry.catalogRefinement` records the residuals, the matched stars and the catalog identity, or why the solver's solution was kept. Pixel values are untouched. Set `"catalogRefit": false` in the recipe's `solver` block to publish the solver's solution unchanged.

The verification matches every star SEP detects on the master, including the bright stars it deblends from a fainter neighbour (`acceptedSourceFlags` 1, SEP's `OBJ_MERGED`, in the recorded correspondence parameters). A deeper stack shows more of those neighbours, and the bright stars it deblends are exactly the ones an all-sky Tycho-2 index holds: with clean detections only, the L master of RCS2 J0327-1326 matched 12 of its 29 Tycho-2 stars from 149 Lights and 10 from 162, below the run's 12, so the refit and with it the whole project failed once more Lights were kept. With deblended stars it matches all 29 at a clipped RMS of 1.0″ (0.92″ on the 12 clean ones). The fits themselves (the refit, a mosaic's joint fit) keep clean detections, so a published WCS and its master change only where a verification's outcome changes. That can go either way: the deblended stars add a little centroid scatter, so a master whose verification sat just under the RMS gate could now miss it. The verification receipts of every run record the new parameter and their new match counts.

The verification reads the all-sky Tycho-2 indexes, which are independent of the Gaia stars of the fit but hold positions from around 1990 and no proper motions. About 35 years on, a star moving 100 mas/yr sits 3.5″ from its catalog position however right the WCS is, so a few such stars can decide the plain RMS. The gate therefore judges `correspondence-clipped-rms-v1` (recorded as `verificationStatistic`), computed from the residual radii `r` of the matched pairs:

- `σ = median(r) / √(2 ln 2)`, the Rayleigh scale of the bulk;
- a pair is an outlier when `r > max(4σ, gate)`;
- the statistic is the RMS of the other pairs, or of all pairs when more than 30 % of them are outliers.

It never exceeds the plain RMS, so a master that passes on the plain RMS still passes. An error of the WCS moves most stars, which raises the median and with it the limit, so the outliers come back into the RMS. The match count still counts every pair, and the match radius and the 2.0″ gate do not change. The master's accepted solve publishes the clipped RMS; the receipt's `rewritten.<filter>` adds `verifiedRawRmsArcsec` and `verifiedOutliers`, a refused refit records them as `verificationResidual`, and `correspondence.json` beside the master holds every pair. On an L stack of SDSS J1004+4112 the plain RMS is 2.10″ on 17 Tycho-2 stars and the clipped RMS 0.99″ with 4 outliers. Shifting that refit by 1″ in declination, rotating it by 5′ or scaling it by 0.1 % leaves no outlier and fails the gate at 2.16″, 2.63″ and 2.24″. The solver's own gate and the verification of a mosaic's canvas still judge the plain RMS.

A filter whose own solve misses a gate does not stop a run when another filter on the same grid solved. Its master takes the grid's lowest-RMS solve and joins the refit, so the refit must also pass catalog verification on that master's own pixels. Without an applied refit (no Gaia-density catalog, no gain on held-out stars, or a master that does not verify) the taken solve is withdrawn and the run fails as before. The receipt's `astrometry.sameGridInheritance` names those filters and the solve they took; their headers carry `OAFWCSSG` and `OAFWCSPR` `INHERITED_SAME_GRID`, and the project receipt labels such a channel `SAME_GRID_CATALOG_VERIFIED` rather than a fresh solve. On RCS2 J0327-1326 (same train), L, G and B solved at 2.47″ on 29 Tycho-2 stars, over the 2.0″ gate, and R at 1.88″. All four took R's solve, which is 2.52″ off on 156 Gaia stars; the refit is 0.147″ (held-out 0.155″), and each master verifies at 0.92–0.95″ on 12–23 catalog stars.

When no filter solved, a solve that missed only the RMS gate takes that place. It must have passed every other check (match count, managed catalog, hints, execution receipt) and read at most 1.5 times the gate, 3.0″ at the default. The lowest-RMS such solve goes to every master of the grid and seeds the refit under the same rule: it is published only with an applied refit, and is otherwise withdrawn and the run fails as before. The 2.0″ gate does not change, and a solve that misses it is never published as it is. The receipt's `sameGridInheritance.adoptedSolve` is `MISSED_ONLY_THE_RMS_GATE` (`ACCEPTED` when a filter solved), and the attempt keeps its plain RMS, its `SOLVER_RMS_ABOVE_MAXIMUM` and the WCS it offered as `refitSeedWcs`.

The solver's RMS does not measure its error on this train, because the solver fits the same stale stars the gate then checks. On 12 masters it reads 1.55–2.48″ while the solution is 2.08–2.61″ RMS off the refit over the field, whether the gate accepted it or not. On RCS2 J0327-1326, B alone and G alone failed at 2.46″ and 2.47″; they now publish order 3 on 202 stars at 0.164″ (held-out 0.18–0.19″), verified on 23 pairs at 0.94″.

The 3.0″ limit comes from 81 seeds on three real masters, 78 of them damaged on purpose. The 55 that read up to 5″ all reach the same WCS as the undamaged seed (0.00″ apart over the field). The first wrong one reads 5.81″ and ends 1.78″ off at the field edge: such a seed matches the catalog in only part of the field, so the fit looks clean on the stars it has (held-out 0.17″) and neither the held-out residual nor the verification sees the error.

Install `astrometry-net-5205-lite` (the Gaia DR2 LITE index 5205, 48 HEALPix tiles, 587 MiB) beside the Tycho-2 set to make the refit work; see the [offline catalog recipe](offline-solver-catalogs.md). The refit needs a catalog dense enough to measure the distortion: at least 60 catalog stars in the field, twice the 30 matches it needs, since about half survive saturation, isolation and matching. The checked Tycho-2 set 4107–4112 holds about 50 stars in that M31 field, so the refit is skipped after a 0.3 s catalog query and the solver's solution is published as before. With a Gaia-density catalog the same master refits to order 3 on 1218 stars in 3.9 s; against the independent half of Gaia, the median residual is 0.058″ and the 90th percentile 0.22″. With the 5205 tiles installed, the managed catalog itself gives order 3 on 123 stars, 0.069″ median and 0.21″ at the 90th percentile against Gaia DR3.
