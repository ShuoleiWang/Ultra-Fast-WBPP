# Windows x64 support

Windows x86-64 (Windows 10 22H2 and Windows 11) is a supported platform of the desktop application and the engine. This page states what is validated, what a Windows machine needs, where Windows behaves differently from macOS, and what is still outside the validated set. The numbers come from the retained hardware run of 2026-09-21 on an AMD Ryzen 7 5800H laptop (8 cores / 16 threads, 16 GB, NVMe, Windows 11 Pro 25H2, build 26200) and from the hosted `windows-latest` CI jobs; see [validation-matrix.md](validation-matrix.md) for the table.

## What a Windows machine needs

- Windows 10 22H2 or Windows 11, x86-64. Windows on ARM64 is refused with `PLATFORM_UNSUPPORTED` (the x64 build would run under emulation without validation); the app's runtime card says so instead of failing inside a run.
- The WebView2 runtime: Windows 11 ships it; the installers carry the Evergreen bootstrapper and install it silently on a Windows 10 machine that lacks it (an offline installer is documented in [release-process.md](release-process.md)).
- No Visual C++ redistributable: the native kernel DLL (`ufwbpp_native.dll`) and the desktop executable link the C runtime statically; the frozen Python engine ships its own interpreter runtime. The bundle attestation walks every DLL/PYD/EXE in the installed engine tree and refuses an import that neither the operating system nor the tree provides.
- A plate solver: [ASTAP](https://www.hnsky.org/astap.htm) (`astap_cli.exe`, found under `Program Files\astap`, on `PATH`, or through `UFWBPP_ASTAP`) with a star database (D20 or larger) next to it, plus the app-managed Astrometry.net index set (4107–4112, about 350 MB, installed from the app's solver panel after explicit acceptance of the provider terms). ASTAP finds the solution; the engine verifies it against the managed index stars, so the same strict final gate applies as on macOS (see below). `solve-field` is used instead when a native build is present.
- Disk space for the run's intermediates: about 12 bytes per pixel per Light on the output volume (registered frames and masters are written there, never to `%TEMP%`).

## The solver route on Windows

Astrometry.net's `solve-field` has no maintained native Windows build, so the Windows final gate is ASTAP with engine-side verification: after `astap_cli.exe` writes a solution (with `-sip` distortion terms when the CLI offers them), the engine detects stars on the final master, projects the Tycho-2 stars of the densest managed index that covers the field through the solved WCS, matches them one to one, and records the residuals, the matched-star count, the parity, the correspondence table and the byte-bound index identities in the receipt — the same evidence, in the same shape, that the astrometry.net adapter produces. The recipe thresholds (`min_matches`, `max_rms_arcsec`) apply unchanged; an unmanaged catalog leaves ASTAP diagnostic-only. On the four NGC 7331 masters (6165 × 4138 pixels, 0.65″/pixel) the verified ASTAP solutions match 26–43 Tycho-2 index stars at 0.62–0.84″ RMS. Compared with the astrometry.net solutions of the same field on macOS (26 matches, 0.94–0.95″ RMS), the two solutions agree to 1–2 pixels over the central 80 % of the field and diverge only in the extreme corners (up to 12″ beyond a radius of 3000 pixels), where ASTAP's order-3 and astrometry.net's order-2 distortion polynomials extrapolate past the fitted stars.

## Behaviour that is specific to Windows

- **Paths.** `MAX_PATH` (259 characters) applies unless the machine policy `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\LongPathsEnabled` is on *and* the running executable opts in (the desktop executable and the frozen engine both declare `longPathAware`; the engine confirms the combination with a real probe rather than trusting the policy). Before any work starts the engine projects the deepest path a run will create (staging directories, per-frame temporaries) and refuses with `OUTPUT_PATH_TOO_LONG` when it would not fit, naming the length, the limit and both remedies (a shorter output folder, or enabling long paths). The staging names are short (`.pstage`, `.stage`, `pp`), and the doctor reports the effective limit (`hardware.pathLimit`). NINA file names with `°`, spaces and CJK characters are handled throughout; the worker's stdio is UTF-8 regardless of the console code page.
- **Environment.** Variable names are resolved case-insensitively wherever the engine reads them (executable discovery under `ProgramFiles`, the solver's restricted environment, data roots), matching how Windows resolves them.
- **File lifecycle.** Antivirus and indexing services hold handles briefly; deletes and renames of the run's own temporaries retry with a bounded back-off on sharing violations, and every cleanup is idempotent. Memory-mapped inputs are released before their files are removed. No symbolic links are created.
- **Processes.** The release executable is a GUI-subsystem binary, so no console window opens next to the app (the bundle attestation checks the subsystem). The desktop runs every worker inside a Job Object with kill-on-close: cancelling a run, or quitting the app during one, terminates the whole tree (`python.exe` pools, `astap_cli.exe`) at once; `taskkill /T` remains the fallback. The command-line engine terminates its own solver processes the same way.
- **Memory.** The number of quality-control and registration workers is bounded by the free memory reported by `GlobalMemoryStatusEx` (about 1.25 GiB per worker after a 2 GiB reserve), so an 8 GB machine runs with fewer workers instead of paging; the receipt records `tuning.qcWorkers` and `tuning.availableMemoryBytes`.
- **Reads.** FITS bands are read with buffered `readinto` calls instead of memory maps (byte-identical values; the memory-mapped path stays the reference on POSIX and can be forced with `LIGHTFRAMEQC_FITS_READER=memmap`).
- **Source extraction.** The PyPI build of SEP 1.4.1 is not deterministic on Windows (its deblending draws from an unseeded `rand()` on MSVC, and Lutz/deblend buffers are left uninitialised on a randomised heap), which made two runs of the same project differ by a star here and there and therefore in the masters. Windows bundles and CI use a patched build (`sep 1.4.1+ufwbpp.1`, [`packaging/patches`](../packaging/patches), built by `scripts/build_sep_wheel.py` from the hash-pinned sdist); the doctor and every receipt carry the result of a determinism self-test (`sourceExtraction.deterministic`), and a run on an unpatched build is marked `SEP_NONDETERMINISTIC`. The patch is behaviour-neutral where the PyPI build was already deterministic (macOS/Linux products are byte-identical with and without it).

## Reproducibility

- **Same machine, same inputs:** two runs of the same project produce bit-identical masters (verified on the laptop with the patched SEP build).
- **Windows versus macOS:** per-frame measurements agree to the rounding of different math libraries; a frame that sits exactly on a gate boundary can be decided differently, which changes the admitted set and therefore the masters. Cross-platform results are compared with the tolerance gate (`tools/validation/master_tolerance_gate.py`), never with file hashes.

## Performance on this class of hardware

On the validation laptop the 61-frame NGC 7331 project runs in 4.5 minutes (267 s and 289 s wall clock for two consecutive runs, solver and verification included; the fused calibrate-and-warp stage takes 59 s) against 76 s on an M3 Pro. Quality control and registration are dominated by star extraction (fixed by the patched SEP build), the fused calibrate-and-warp stage by memory bandwidth, and the integration by per-core speed; the kernels use every logical core (SMT threads are 37 % faster than physical cores alone on the Ryzen). Windows Defender's real-time scanning of the output folder costs a few percent; an exclusion is a user decision and is never written by the app.

## Validated and not validated

Validated: the hosted CI matrix (Windows Server 2022/2025, the bundle's Python 3.12, MSVC `/W4 /WX /fp:strict` kernels value-identical to the NumPy references, Rust Job Object and process-tree tests, the installed MSI attestation in the release workflow) and the laptop run of 2026-09-21 (build, full test suite, the real 61-frame project through the command line twice and once more through the worker of the installed MSI under a minimal environment — all three runs bit-identical in every product — verified solutions on all four masters, and the installed-MSI gate: import closure of 260 PE images, static CRT, GUI subsystem, launch budget, clean uninstall). A hands-on session through the Windows GUI on real hardware is still to be recorded; the process-tree termination and progress-stream behaviour it depends on is covered by the Windows CI tests.

Not validated: Windows 10 on real hardware (CI covers the Windows 10 kernel family through Windows Server 2022), Intel hybrid (P/E-core) processors and machines with 8 GB or with a spinning disk — their tuning rows are exercised with simulated topology and memory inputs in the unit tests, and every platform fact in a receipt carries its source so a fallback is visible. Authenticode signing is a release gate that the unsigned prerelease does not meet (SmartScreen shows "Windows protected your PC → More info → Run anyway"; the MSI shows the unknown-publisher prompt). GPU acceleration is not used on any platform.

## Developing on Windows

`scripts/windows/bootstrap.ps1` installs the toolchain (Python 3.12, CMake, Ninja, Visual Studio Build Tools, optionally Rust); `scripts/windows/dev-env.ps1` prepares a shell. With a portable MSVC (no Visual Studio installation) set `DISTUTILS_USE_SDK=1` and `MSSdk=1` so setuptools builds the SEP wheel with the environment's `cl`. When copying a tree from macOS, export `COPYFILE_DISABLE=1` before `tar` so no AppleDouble `._*` files arrive. See [`scripts/windows/README.md`](../scripts/windows/README.md).
