# Windows backend contract — not a current support claim

Windows (x86-64, Windows 10/11) is a first-class design boundary while the only retained hardware/scientific acceptance is on macOS M3 Pro. Hosted Windows Python 3.11/3.12, Rust, and native C++ jobs are configured for the desktop GUI, project/recipe schemas, worker protocol, filesystem boundary, and portable CPU algorithms; the current uncommitted candidate still needs its first authorized public CI run. This remains an interface, compilation, and synthetic-test target: a packaged Windows E2E, real scientific acceptance, installed-runtime attestation, installer smoke, and signing are all required before the first Windows release.

Phase 0 of the Windows plan is in place: the platform service layer (`openastroflow_engine.platform`) measures memory with `GlobalMemoryStatusEx` and the core topology with `GetLogicalProcessorInformationEx` instead of assuming 8 GiB; the x86-64 tuning row (`windows-x86-64-cpu-v1`) is a table keyed by memory and cores; the native kernels build with MSVC 2022 (`/W4 /WX /fp:strict`) through `scripts/build_native_runtime.py`, the Windows CI job installs the DLL before the Python tests so `test_native_kernels.py` proves the kernels value-identical to NumPy on Windows, the sidecar builder refuses a frozen worker that cannot load the DLL and collects it as a PyInstaller binary so the MSVC runtime ships with it; `ParallelRange` claims dynamic chunks so hybrid Intel P/E cores and SMT siblings never stall a range. `scripts/windows/bootstrap.ps1` installs the toolchain with winget. Phase 1 has started: the platform service layer also owns the create-only directory rename and file publication (with a rename fallback on volumes without hard links), directory flush (`FlushFileBuffers`), volume facts (`GetVolumeInformationW`), cache/data roots, child-process isolation and `taskkill /T` tree termination, keep-awake (`SetThreadExecutionState`) and the well-known executable locations, and the previously duplicated copies in the engine call it. The solver route (§9 of the plan), Job Objects in the desktop process control, memmap-release hygiene around deletions, CUDA and the release gates remain open.

The current app-core has a conservative standard-library `PlatformFs` contract with create-new files/directories, no-follow metadata checks, hashing and completion-last publication. It is not yet the release-grade Windows adapter: handle-based stable file IDs, reparse-point component checks, `FlushFileBuffers`, volume identity and documented directory-durability behavior are still implementation gates. Serialized v1 project messages currently carry display/host paths as strings; the planned opaque file-capability mapping must replace direct GUI path authority before the Windows release.

The first Windows scientific backend is CPU-correctness oriented. A future `wgpu`/DirectX 12 backend must be an additional capability with the same recipe and differential gates; it cannot replace the CPU oracle. ASTAP and Siril are optional external programs under their own licenses, while Astrometry.net on Windows normally requires a separately installed compatible environment; ASTAP remains diagnostic-only for the strict final gate. Until the handle/reparse implementation and Windows CI/package tests pass, the GUI may show the Windows CPU seam but must label execution unavailable.
