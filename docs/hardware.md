# Apple Silicon support

Ultra-Fast WBPP targets one arm64 macOS application for Apple M-series systems. The generic execution design selects CPU, memory, and Metal capabilities rather than a hard-coded product-name whitelist, but the current retained hardware evidence covers only a 36 GiB M3 Pro. A non-M3 machine can report `compatible-generic`; it must not report `performance-validated` until that exact release matrix has run on representative hardware.

The wire profile is OS-specific: Linux x86-64 uses `portable-cpu`, Windows uses the unvalidated `windows-cpu` seam, and Apple arm64 uses `generic-arm64-cpu`. `generic-apple-metal` and `m3-pro-tuned` are advertised only after constructing a real `NativeMetalExecutor`; an Apple architecture string alone is insufficient. A missing dylib, unavailable device, ABI failure, or throwing probe leaves the canonical CPU handshake usable. Tile sizes and concurrent buffers derive from pipeline width, thread execution width, maximum buffer length, recommended working-set size, physical memory, and recipe peak estimates. If later execution gates fail, the task returns to CPU without changing the scientific recipe.

M3 Pro additionally enables `m3-pro-tuned`, whose parameters are accepted only after differential tests against the CPU oracle and real-data performance measurements. The tuned profile targets bounded I/O, CPU decode/model fitting overlapped with Metal warp/normalization/integration, reusable buffers, and unified-memory pressure. It does not enable fast-math or weaker rejection/WCS thresholds.

The retained private full-B fixture uses 38 QHY268M Lights, 20 raw Flats, and supplied normalized-XISF MasterBias/MasterDark. Its complete QC, calibration, full-resolution transform refinement, domain-bounded Lanczos-3 registration, global normalization, rejection/integration, managed solve, and publication path took 466.116 seconds and passed all 25 independent PixInsight-reference checks. This is evidence for that one M3 Pro/camera/filter/observing condition, not a speed guarantee or an algorithmic-equivalence claim. The Lanczos-3 correctness fix adds most of the current wall time; moving the same kernel into native CPU/Metal is an optimization target, while returning to bilinear registration is not acceptable.

The current measured 36 GB M3 Pro profile caps the orchestration layer at eight CPU workers, QC readers at two, Metal work at two in-flight buffers, and integration tiles at 64 rows. An M3 Pro with less than 24 GiB deliberately falls back to generic Apple-Silicon tuning. Generic M-series profiles scale from one worker/24-row tiles below 12 GiB to four workers/48-row tiles at 24 GiB or more; all memory budgets reserve at least 38% for the OS, file cache, GUI, and temporary arrays.

The ordinary-integration implementation applies those tile and in-flight-buffer values directly. CPU generates the full-stack median/MAD rejection mask while queued Metal work reduces the preceding tile. Stacks up to 512 frames remain one mathematical reduction rather than averages of batches. Metal/library/resource/parity failure restarts the group through the portable CPU path and writes the fallback reason plus `inputFramesTruncated=false` into the receipt.

The arm64 `macos-14` native Metal compile/differential job and separate CPU-only canonical handshakes are configured in the hosted workflow; the current local candidate still requires its first authorized public green run. Hosted compile/differential evidence would not be retained non-M3 scientific or performance acceptance: a release support claim still requires evidence from at least one non-M3 Apple Silicon machine. Until a specific family is represented in the release matrix, the application reports it as compatible through the generic profile rather than performance-validated.
