# Apple Silicon support

Ultra-Fast WBPP targets one arm64 macOS application, macOS 15 or later, for Apple M-series systems. The generic execution design selects CPU, memory, and Metal capabilities rather than a hard-coded product-name whitelist, but the current retained hardware evidence covers only a 36 GiB M3 Pro. A non-M3 machine can report `compatible-generic`; it must not report `performance-validated` until that exact release matrix has run on representative hardware.

The wire profile is OS-specific: Linux x86-64 uses `portable-cpu`, Windows uses `windows-cpu` (validated on x64, see [windows.md](windows.md)), and Apple arm64 uses `generic-arm64-cpu`. Below the wire profile, the tuning row is a table keyed by platform, CPU family, memory band and core count: Apple silicon rows as described below, and one x86-64 row per platform (`windows-x86-64-cpu-v1`, `linux-x86-64-cpu-v1`: two workers below 12 GiB, four below 24 GiB, eight above, always bounded by the logical core count) whose evidence class stays `compatible-generic` until a machine of that class has retained acceptance evidence (the Ryzen 7 5800H 8C/16T, 16 GiB class has). On Windows the quality-control and registration worker count is additionally bounded by the free memory reported by `GlobalMemoryStatusEx` — one worker per 1.25 GiB after a 2 GiB reserve — so an 8 GB machine keeps two workers instead of paging; the receipt records `tuning.qcWorkers` and `tuning.availableMemoryBytes`. The kernels keep every logical core: on the Ryzen the 16 SMT threads run the Lanczos warp 37 % faster than its 8 physical cores. Memory and core counts come from the platform service layer (`GlobalMemoryStatusEx`/`GetLogicalProcessorInformationEx` on Windows, `sysctl` on macOS), and receipts name the source of each fact. Each row also carries a native-kernel thread budget (`kernelThreads`) that is distinct from the memory-bound worker count: the x86-64 rows give the kernels every logical core, the M3 Pro row gives them its twelve logical cores, and the generic Apple silicon rows keep the worker count. `generic-apple-metal` and `m3-pro-tuned` are advertised only after constructing a real `NativeMetalExecutor`; an Apple architecture string alone is insufficient. A missing dylib, unavailable device, ABI failure, or throwing probe leaves the canonical CPU handshake usable. Tile sizes and concurrent buffers derive from pipeline width, thread execution width, maximum buffer length, recommended working-set size, physical memory, and recipe peak estimates. If later execution gates fail, the task returns to CPU without changing the scientific recipe.

M3 Pro additionally enables `m3-pro-tuned`, whose parameters are accepted only after differential tests against the CPU oracle and real-data performance measurements. The tuned profile targets bounded I/O, CPU decode/model fitting overlapped with Metal warp/normalization/integration, reusable buffers, and unified-memory pressure. It does not enable fast-math or weaker rejection/WCS thresholds.

The retained private full-B fixture uses 38 QHY268M Lights, 20 raw Flats, and supplied normalized-XISF MasterBias/MasterDark. Its complete QC, calibration, full-resolution transform refinement, domain-bounded Lanczos-3 registration, global normalization, rejection/integration, managed solve, and publication path took 466.116 seconds and passed all 25 independent PixInsight-reference checks. This is evidence for that one M3 Pro/camera/filter/observing condition, not a speed guarantee or an algorithmic-equivalence claim. That run predates the native kernels: its Lanczos-3 warp ran in NumPy and accounted for most of the wall time. The same warp now runs in the multithreaded native kernel with value-identical output; returning to bilinear registration is not acceptable, and the retained 466-second figure is a historical measurement, not the current baseline (see the native-kernel benchmark in [benchmarks](../benchmarks/README.md)).

The current measured 36 GB M3 Pro profile runs the orchestration layer with twelve CPU workers and twelve native-kernel threads (one per logical core: with the kernels' dynamic chunking the six efficiency cores add about 20% warp throughput over the earlier eight-thread setting, and no result depends on either count), eight QC readers, Metal work at two in-flight buffers, and integration tiles at 64 rows. An M3 Pro with less than 24 GiB deliberately falls back to generic Apple-Silicon tuning. Generic M-series profiles scale from two workers/24-row tiles below 12 GiB, through four workers/32-row tiles below 24 GiB, to eight workers/48-row tiles at 24 GiB or more, always bounded by the logical core count; all memory budgets reserve at least 38% for the OS, file cache, GUI, and temporary arrays. The registration budget (a sixth of usable memory, at most 4 GiB) decides how many decoded Lights are calibrated and warped concurrently; the native kernels split each warp and each integration tile across the remaining cores, so a memory-limited machine still uses every core.

The ordinary-integration implementation applies those tile and in-flight-buffer values when the Metal path is requested explicitly: CPU generates the full-stack median/MAD rejection mask while queued Metal work reduces the preceding tile. With `auto`, an Apple silicon machine whose native kernel library is loaded runs the multithreaded native CPU rejection and reduction instead, because the rejection statistics dominate and the Metal reduction's host-side normalization, copies and parity reruns cost more than its GPU time; the receipt records `selectionPolicy: native-cpu-kernels-preferred`. Stacks up to 512 frames remain one mathematical reduction rather than averages of batches. Metal/library/resource/parity failure restarts the group through the portable CPU path and writes the fallback reason plus `inputFramesTruncated=false` into the receipt.

An application started from the Finder gets a soft limit of 256 open files (`launchctl limit maxfiles`), and an integration holds two descriptors for every open Light, so a group of more than about 125 Lights failed with `Too many open files`. The engine raises its soft limit to 10,240 (or the hard limit) when it starts. An output folder may be on an exFAT external disk: macOS answers `ENOTSUP` there to both the hard link and `renamex_np(RENAME_EXCL)`, and the engine publishes through its create-only fallbacks instead (an exclusive create and a rename onto the empty file; a `mkdir` claim and a rename onto the empty directory). That was run with the synthetic pixel pipeline on a real exFAT disk image, which published the same 17 files byte for byte as on APFS; a full project on exFAT, FAT32 or a network share has not been run.

With `UFWBPP_DISABLE_NATIVE_KERNELS=1`, integration's `auto` backend takes the portable CPU path with the NumPy reference, not Metal; a run that collects tiles (selection evidence, drizzle masks) is never sent to Metal.

Hosted CI has no Metal job: the `Apple Silicon Metal compile/differential` job was removed because its runners expose no Metal device and always skipped the differential. The `macos-15` Python job still builds the Release kernels with Metal, ctest-checks and installs them, with the CPU↔Metal differential skipped there, so a Metal change is verified with `make native-test` on Apple Silicon hardware. CI results are not scientific or performance acceptance for non-M3 machines: a release support claim still requires evidence from at least one non-M3 Apple Silicon machine. Until a specific family is represented in the release matrix, the application reports it as compatible through the generic profile rather than performance-validated.
