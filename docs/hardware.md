# Apple Silicon support

Ultra-Fast WBPP targets one arm64 macOS application for Apple M-series systems. The generic execution design selects CPU, memory, and Metal capabilities rather than a hard-coded product-name whitelist, but the current retained hardware evidence covers only a 36 GiB M3 Pro. A non-M3 machine can report `compatible-generic`; it must not report `performance-validated` until that exact release matrix has run on representative hardware.

The wire profile is OS-specific: Linux x86-64 uses `portable-cpu`, Windows uses the unvalidated `windows-cpu` seam, and Apple arm64 uses `generic-arm64-cpu`. Below the wire profile, the tuning row is a table keyed by platform, CPU family, memory band and core count: Apple silicon rows as described below, and one x86-64 row per platform (`windows-x86-64-cpu-v1`, `linux-x86-64-cpu-v1`: two workers below 12 GiB, four below 24 GiB, eight above, always bounded by the logical core count) whose evidence class stays `compatible-generic` until a machine of that class has retained acceptance evidence. Memory and core counts come from the platform service layer (`GlobalMemoryStatusEx`/`GetLogicalProcessorInformationEx` on Windows, `sysctl` on macOS), and receipts name the source of each fact. Each row also carries a native-kernel thread budget (`kernelThreads`) that is distinct from the memory-bound worker count: the x86-64 rows give the kernels every logical core, the M3 Pro row keeps its validated eight, and the generic Apple silicon rows keep the worker count. `generic-apple-metal` and `m3-pro-tuned` are advertised only after constructing a real `NativeMetalExecutor`; an Apple architecture string alone is insufficient. A missing dylib, unavailable device, ABI failure, or throwing probe leaves the canonical CPU handshake usable. Tile sizes and concurrent buffers derive from pipeline width, thread execution width, maximum buffer length, recommended working-set size, physical memory, and recipe peak estimates. If later execution gates fail, the task returns to CPU without changing the scientific recipe.

M3 Pro additionally enables `m3-pro-tuned`, whose parameters are accepted only after differential tests against the CPU oracle and real-data performance measurements. The tuned profile targets bounded I/O, CPU decode/model fitting overlapped with Metal warp/normalization/integration, reusable buffers, and unified-memory pressure. It does not enable fast-math or weaker rejection/WCS thresholds.

The retained private full-B fixture uses 38 QHY268M Lights, 20 raw Flats, and supplied normalized-XISF MasterBias/MasterDark. Its complete QC, calibration, full-resolution transform refinement, domain-bounded Lanczos-3 registration, global normalization, rejection/integration, managed solve, and publication path took 466.116 seconds and passed all 25 independent PixInsight-reference checks. This is evidence for that one M3 Pro/camera/filter/observing condition, not a speed guarantee or an algorithmic-equivalence claim. That run predates the native kernels: its Lanczos-3 warp ran in NumPy and accounted for most of the wall time. The same warp now runs in the multithreaded native kernel with value-identical output; returning to bilinear registration is not acceptable, and the retained 466-second figure is a historical measurement, not the current baseline (see the native-kernel benchmark in [benchmarks](../benchmarks/README.md)).

The current measured 36 GB M3 Pro profile caps the orchestration layer at eight CPU workers and eight QC readers, Metal work at two in-flight buffers, and integration tiles at 64 rows. An M3 Pro with less than 24 GiB deliberately falls back to generic Apple-Silicon tuning. Generic M-series profiles scale from two workers/24-row tiles below 12 GiB, through four workers/32-row tiles below 24 GiB, to eight workers/48-row tiles at 24 GiB or more, always bounded by the logical core count; all memory budgets reserve at least 38% for the OS, file cache, GUI, and temporary arrays. The registration budget (a sixth of usable memory, at most 4 GiB) decides how many decoded Lights are calibrated and warped concurrently; the native kernels split each warp and each integration tile across the remaining cores, so a memory-limited machine still uses every core.

The ordinary-integration implementation applies those tile and in-flight-buffer values when the Metal path is requested explicitly: CPU generates the full-stack median/MAD rejection mask while queued Metal work reduces the preceding tile. With `auto`, an Apple silicon machine whose native kernel library is loaded runs the multithreaded native CPU rejection and reduction instead, because the rejection statistics dominate and the Metal reduction's host-side normalization, copies and parity reruns cost more than its GPU time; the receipt records `selectionPolicy: native-cpu-kernels-preferred`. Stacks up to 512 frames remain one mathematical reduction rather than averages of batches. Metal/library/resource/parity failure restarts the group through the portable CPU path and writes the fallback reason plus `inputFramesTruncated=false` into the receipt.

The arm64 `macos-14` native Metal compile/differential job and separate CPU-only canonical handshakes are configured in the hosted workflow; the current local candidate still requires its first authorized public green run. Hosted compile/differential evidence would not be retained non-M3 scientific or performance acceptance: a release support claim still requires evidence from at least one non-M3 Apple Silicon machine. Until a specific family is represented in the release matrix, the application reports it as compatible through the generic profile rather than performance-validated.
